# ADR 138 — Production Tailscale Private Transport Foundation V1

**Status:** Accepted  
**Scope:** P11 production CI/CD transport foundation  
**Date:** 2026-08-25

## Context

SRCM first established the production deployment workflows while the host variable still represented the VPS public IPv4 transport. The production security work later moved SSH authorization behind Tailscale, restricted the dedicated deploy identity to the private overlay origin, and proved the complete WIF + Tailscale + pinned OpenSSH path with the dedicated read-only Safe Smoke workflow.

A GitHub-hosted job is an isolated execution boundary. Therefore a successful Tailscale connection created by the Safe Smoke workflow is evidence for the transport design, but it is not network state that bootstrap or normal deployment jobs can inherit. Every protected job that performs production remote I/O must establish and verify its own private route.

## Decision

The protected remote-I/O jobs in both production workflows must compose the already-proven private transport before SSH or SCP:

1. The remote-I/O job receives `id-token: write` only where WIF is needed while retaining `contents: read`.
2. It connects with the exact pinned action `tailscale/github-action@780049a30b6ff5c378a9e7b389d15ece7a204888` (`v4.1.3`).
3. WIF inputs come only from the protected `production` environment secrets `TS_OAUTH_CLIENT_ID` and `TS_AUDIENCE`.
4. The ephemeral CI node uses tag `tag:straleon-ci-deploy`.
5. Before any SSH/SCP, `SRCM_DEPLOY_HOST` must equal the private target `100.64.245.55`, deploy user must equal `straleon-deploy`, port must equal `22`, the runner must have a Tailscale IPv4, and `ip route get` must prove `dev tailscale0`.
6. The private deploy key must match fingerprint `SHA256:x6L1N7kD+rcrlqD7EB+boZgwDQc4AtO6NMMltEHZhpw` and the pinned target host key must match `SHA256:iy4hCZtEYlqi3MjSxLFmX7cKPTFXXfecZultd7c2Xj4` before remote I/O.
7. The public VPS IPv4 `64.176.3.12` is not a valid workflow transport target after this foundation.

The source authorization boundary remains before the Tailscale action. A workflow whose release/source gates are false exits before private network access is established.

## Fail-closed staging

This ADR does **not** authorize a production release. In this cut:

- `production_release_enabled` remains `false`;
- `initial_application_release_bootstrap_enabled` remains `false`;
- `external_gates.production_environment_secrets_and_approvals` remains `false`;
- no workflow is dispatched;
- no GitHub Environment variable or secret is changed;
- no server, application, service, symlink, release directory, or production database is mutated.

The existing GitHub Environment `SRCM_DEPLOY_HOST` value is intentionally not changed by this source-only foundation. Migration of that control-plane variable from its historical public IPv4 value to `100.64.245.55` requires a later, separately evidenced authorization/configuration cut. Until then, even after source authorization is eventually opened, the exact private-target assertion prevents remote I/O through the legacy value.

## Verification contract

`ReleasePreflightInspector` and `ProductionDeploymentFoundationTest` must fail if either production remote workflow loses OIDC permission, changes the pinned Tailscale action, changes WIF inputs/tag, removes the exact private target/user/port guard, loses the `tailscale0` route proof, loses either SSH fingerprint pin, contains the historical public IPv4, or moves SSH configuration before the private-route proof.

## Consequences

Production transport becomes explicit and reproducible per protected GitHub job instead of depending on evidence generated by another runner. The next step is not deployment: it is evidence that this source foundation is published under normal branch governance and then a separately controlled migration of the production Environment host variable to the private Tailscale address.
