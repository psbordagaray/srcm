# Principios de SRCM

Los siguientes principios definen la filosofía de diseño de SRCM.

Ante cualquier duda técnica o funcional, deberá priorizarse siempre el cumplimiento de estos principios.

---

# 1. El usuario no trabaja para el sistema.

El sistema trabaja para el usuario.

SRCM debe reducir trabajo, no generarlo.

---

# 2. Una información correctamente registrada no debe volver a escribirse.

Si un dato ya existe y puede reutilizarse, el sistema deberá evitar solicitarlo nuevamente.

---

# 3. El usuario valida.

SRCM propone.

Siempre que sea posible, el sistema reconocerá automáticamente información y solicitará únicamente la confirmación del usuario.

---

# 4. Primero el conocimiento.

Después las operaciones.

Las operaciones cambian constantemente.

El conocimiento permanece y crece.

---

# 5. El Catálogo Maestro pertenece al ecosistema.

No pertenece a un comercio.

No pertenece a una persona.

Representa conocimiento compartido.

---

# 6. La información privada pertenece exclusivamente a su organización.

Clientes.

Ventas.

Compras.

Costos.

Stock.

Márgenes.

Todo ello es privado.

---

# 7. Ningún Sprint podrá hipotecar la arquitectura futura.

Toda decisión deberá permitir la evolución del sistema.

Nunca deberá resolverse un problema actual creando un problema mayor para el futuro.

---

# 8. Todo debe poder ampliarse.

Sin romper datos existentes.

Las migraciones enriquecen.

No destruyen.

---

# 9. Las personas son únicas.

Los roles cambian.

Un cliente puede convertirse en proveedor.

Un técnico puede crear una empresa.

La persona continúa siendo la misma.

---

# 10. El conocimiento mejora con la comunidad.

Cada corrección.

Cada compatibilidad.

Cada fotografía.

Cada solución.

Hace mejor a todo SRCM.

---

# 11. La simplicidad siempre tiene prioridad.

Si dos soluciones producen el mismo resultado, deberá elegirse la más simple.

---

# 12. El tiempo del profesional debe dedicarse a resolver problemas.

No a cargar información repetitiva.

---

# 13. El éxito de SRCM se mide por el tiempo que ahorra.

No por la cantidad de funciones que posee.

---

# 14. Programar menos.

Pensar más.

Cada hora de arquitectura evita muchas horas de reescritura futura.
